## 1. Project context

- **Who:** Mahad Faruqi (mfaruqi@purdue.edu), Purdue EcoAI Lab, advisor Dr. Haoran You.
  The proposal is at `proposal/On-DeviceDiffusionProposal.pdf`.
- **Thesis:** a shared compiler/runtime deployment workflow for diffusion models on
  resource-constrained devices. It measures end-to-end and per-stage latency, peak memory and output
  quality, then develops one focused optimization chosen from profiling (precision, kernels,
  memory management, or cross-step reuse).
- **Workloads:** FLUX.2 [klein] 4B for text-to-image (distilled, 4 steps), then Wan 2.1 T2V-1.3B for video.
- **Devices:** NVIDIA A100 on Purdue's Gilbreth cluster (CUDA reference), Jetson Orin Nano (8 GB
  shared CPU/GPU memory; arrives ~2026-09-25), and an M1 MacBook Pro (Metal, week 2).
- **Research questions:**
  - RQ1: do configurations transfer across devices?
  - RQ2: how do quality requirements change the preferred configuration?
  - RQ3: one compiler/runtime improvement that closes a measured gap.
- **Baselines to compare against later:** stable-diffusion.cpp, edge-dit.cpp, FastVideo, and
  PrismML Bonsai (compressed klein). IREE is a candidate compiler.
- **Evaluation rules from proposal §6:**
  - Report cold start separately from warm runs.
  - Report medians and variability.
  - Keep allocator memory separate from device/system memory, and don't double-count shared memory on the Jetson.
  - Quality: GenEval, plus blinded paired visual review.
  - Use separate prompt sets for choosing configurations and for held-out evaluation.
  - Report compressed checkpoints separately from execution-only changes.
- **Week 1 (Sep 28–Oct 2) task in the user's words:** "Establish A100 and Jetson image baselines;
  check related work and define the bounded planning hypothesis."

- Protocol: 1 first + 3 warm-up + 10 measured runs. Timing covers encode + denoise + decode + conversion
  to a PIL image, and excludes model load and saving the image.
- `--profile` adds one separate profiler generation with stage labels, excluded from the statistics.

## 4. What each file does

- **`configs/a100-flux-klein-bf16.json`:** the workload, protocol (1/3/10 runs, 20 ms memory sampling) and an
  `optimizations` block that is all off. `--prepare-only` writes `*.resolved.json` next to it with
  the pinned commit, and GPU runs **require** the resolved config.
- **`scripts/run_flux.py`:** the runner.
  - `prepare()`: resolves the revision with `HfApi.model_info`, then `snapshot_download` with
    `allow_patterns`, so only the diffusers folders are fetched, not the single-file checkpoint.
  - `DeviceMemorySampler`: a background thread that reads NVML (`libnvidia-ml.so.1` via ctypes)
    device-wide used memory every 20 ms.
  - `StageRecorder`: wraps `pipe.encode_prompt`, `pipe.vae.decode` and `pipe.image_processor.postprocess`,
    and adds forward pre/post hooks on `pipe.transformer`. Diffusers source is **not** modified.
    - Each stage records a CUDA event at start and end, with no sync, so execution is unchanged.
    - Each stage also opens a `record_function` label (`text_encode`, `denoise_step_i`, `vae_decode`, `postprocess`) for profiler traces.
    - The allocator peak is reset at every stage boundary, so each stage and each gap between stages gets its own peak.
  - `benchmark()`:
    - Asserts CUDA is present, no optimizations, BF16, and a pinned hash.
    - Loads with `local_files_only`, timing `from_pretrained` and `.to("cuda")` separately.
    - Records per-component weight sizes, then runs the protocol with a fresh `torch.Generator("cuda").manual_seed(seed)` each run.
    - Writes `runs.csv`, `stages.csv`, `memory_segments.json`, `summary.json`, `load.json`, `environment.json`, `environment-freeze.txt`, `scheduler.json`, `nvidia-smi.txt`, `images/first.png`, `images/measured-0.png` and `status.json`.
    - Asserts exactly `num_inference_steps` transformer calls, which confirms no CFG.
    - Hashes every image (sha256) to check determinism.
  - `run_profile()`: one extra generation under `torch.profiler` (CPU+CUDA, shapes, memory). Writes
    `profile/trace.json` (git-ignored), `op_table.txt` and `profiled_run.json`.
- **`scripts/gilbreth.slurm`:**
  - Defaults: `--account=you139 --partition=a100-40gb --qos=normal`, 1 GPU, 4 CPUs, 64 GB RAM, 30 min, log at `logs/flux-baseline-%j.out`.
  - Calls `flux_env/bin/python` directly, so no activation is needed.
  - Sets `HF_HOME` to scratch and `HF_HUB_OFFLINE=1`.
  - `CONFIG` and `PROFILE=1` can be set with `sbatch --export=ALL,...`.
- **`notes/baseline-metrics.md`:** the canonical definition of every metric: what each includes and excludes, which
  numbers must never be added (allocated vs reserved), and the Jetson shared-memory rule.
- **`notes/gilbreth-howto.md`:** what Slurm is, a command cheat sheet, the project setup, storage rules and the run procedure.
- **`notes/a100-flux-klein-001.md`:** the experiment note with full results, profile table, observations and interpretation.
- **`notes/research-log.md`:** dated log, newest entries first.
- **`results/README.md`:** index of runs and a description of each file in a run directory.
- **`.gitignore`:** weights, logs, images, traces, `flux_test/*.json|png`, swap files.
- **`flux_test/`:** the user's earlier exploratory scripts (FLUX.1-schnell, 512²). They are **not** the baseline and
  were kept only for reference.

## 5. Results (A100-PCIE-40GB, jobs 11807390 + 11807396)

- **End-to-end, warm:** median **1240.6 ms**, range 1233–1245, 0.9% spread.
  - Text encode: 47 ms (3.8%).
  - Denoise: 981 ms (79.1%), about 245 ms per step.
  - VAE decode: 165 ms (13.3%).
  - Postprocess: 39 ms (3.2%).
  - Other: 8 ms.
- **First run:** 3163 ms, mostly one-time costs in text encode and VAE.
- **Cached load:** 13.7 s, of which 11.8 s is `.to("cuda")`, because the weights are memory-mapped.
- **Memory:**
  - Weights: text encoder 7.49, transformer 7.22, VAE 0.16 GiB (14.87 total).
  - Peak allocated: **17.32 GiB, set by VAE decode**.
  - Reserved: 19.60 GiB. NVML device-wide: 20.61 GiB.
  - Host peak RSS: 8.0 GiB.
- **Repeatability:** outputs bit-identical across runs. The second job agreed within 0.3%.
- **Profiler, whole generation:**
  - GEMM 44%, flash attention 13%.
  - About a third goes to memory-bound elementwise/norm/cat/copy ops, which are fusion candidates.
  - The breakdown within a single denoise step has not been extracted from the trace yet.
- **Interpretation:**
  - BF16 can't fit the 8 GB Jetson.
  - Three levers: (1) transformer compute/precision, (2) text-encoder residency (50% of weights for 4%
    of time, and never needed together with the VAE peak), (3) the VAE activation peak.
  - Levers 2 and 3 suggest a candidate *bounded planning hypothesis* (stage residency and memory
    planning under a budget). A related-work check is still needed.
