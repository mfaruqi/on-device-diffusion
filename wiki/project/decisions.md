# Decisions

Each record: date, decision, why, evidence, revisit if. New records go at the end of Current. A
superseded record moves to Archive with a link to the one that replaced it.

## Current

### D-001: Reference configuration and one change per labelled configuration
- **Date**: 2026-09-23
- **Decision**: The reference on every device is BF16, batch 1, 1024², 4 steps, guidance 1.0, pinned
  checkpoint revision, no quantization, offload, tiling or compilation. Every variant is a separate
  config that changes exactly one thing, and runners fail instead of falling back.
- **Why**: The proposal requires execution-only changes to be kept apart from changed checkpoints, and
  combinations to be measured together ([overview](overview.md#evaluation-rules)).
- **Evidence**: [a100-flux-klein-001](../../experiments/a100-flux-klein-001.md) is the first reference.
- **Revisit if**: the proposal's workload definition changes.

### D-002: Pin Gilbreth jobs to A100-PCIE nodes
- **Date**: 2026-09-25
- **Decision**: All Slurm scripts request `--constraint=G` (A100-PCIE-40GB, 250 W).
- **Why**: The `a100-40gb` partition mixes PCIE and SXM4 (400 W) nodes, and the same sd.cpp configuration
  ran 5.6% faster on SXM4 ([finding](../findings/a100-sxm4-runs-faster-than-a100-pcie.md)).
- **Revisit if**: the reference moves to another GPU type; all references then get re-run on it.

### D-003: stable-diffusion.cpp reference settings
- **Date**: 2026-09-25
- **Decision**: All weights and compute on `cuda0`; auto-fit off; graph segmentation disabled; eager load;
  conditioning cache 0; flash attention in the diffusion model only. The wrapper fails if the log
  shows otherwise.
- **Why**: sd.cpp's defaults turn on automatic placement and a conditioning cache, which would change
  what is measured ([sd.cpp how-to](../methods/sdcpp-howto.md#reference-settings-and-why-each-one-is-set)).
  Its automatic fitting is still a proposal baseline and will run as its own labelled configuration.
- **Revisit if**: sd.cpp changes these defaults.

### D-004: Drive sd.cpp through a load-once harness, not `sd-cli`
- **Date**: 2026-09-25
- **Decision**: `engines/sdcpp/bench.cpp` links the sd.cpp library, loads once, then generates N times,
  with stage times taken from sd.cpp's callbacks.
- **Why**: `sd-cli` reloads the model on every call, and `--batch-count` encodes the text once per batch,
  so neither can reproduce the 1 + 3 + 10 protocol ([record](../../experiments/a100-sdcpp-flux-klein-001.md)).
- **Revisit if**: sd.cpp adds a benchmark mode.

### D-005: Cross-engine memory uses NVML device-wide numbers only
- **Date**: 2026-09-25
- **Decision**: Only `device_used_peak_gib` is compared across engines. Engine wrappers never create a
  CUDA context of their own.
- **Why**: Allocator metrics exist only for PyTorch ([metrics](../methods/baseline-metrics.md#memory)).
- **Revisit if**: a shared-memory device (Jetson) needs a system-memory metric, which gets defined in the metrics doc first.

### D-006: Shared initial noise from sd.cpp's Philox RNG (proposed)
- **Date**: 2026-09-26
- **Decision (proposed, not implemented)**: The canonical initial noise for each (seed, resolution) is
  generated by sd.cpp's own RNG code, built from the pinned checkout, and saved with its sha256. PyTorch
  runs pass it as `latents=`, and sd.cpp reproduces it from the seed.
- **Why**: Both engines use the same latent shape and memory order, but different RNGs. A numpy port
  matched sd.cpp only to ~1 ulp, so the C++ code is the source ([concept](../concepts/initial-noise.md)).
- **Revisit if**: an engine can't accept external latents.

### D-007: Results stay in run directories; viewer undecided

- **Revisit if**: the advisor recommends a lab tool.

### D-009: Prioritize image-engine baselines and profiling
- **Date**: 2026-10-01
- **Decision**: Prioritize deeper A100/Jetson profiling, edge-dit.cpp feasibility, and controlled
  tests of existing engine options; temporarily defer FastVideo and further DreamLite work
  ([meeting memo](../../raw/meetings/2026-10-01-haoran-you.md#discussed)).
- **Why**: Identify actual compute, transfer and host overhead, audit sd.cpp auto-fit decisions,
  and evaluate caching before expanding the experiment set ([actions](../../raw/meetings/2026-10-01-haoran-you.md#to-do)).
- **Candidate boundary**: LightX2V and TensorRT are suggestions to screen, not selected or validated
  baselines ([actions](../../raw/meetings/2026-10-01-haoran-you.md#to-do), [reading list](../papers/reading-list.md)).
- **Scope**: Weeks 1-2 baselines and Weeks 3-4 analysis/instrumentation; primarily RQ1, with measurements
  feeding RQ2/RQ3. The [proposal's targets and RQs](overview.md) remain unchanged.
- **Revisit if**: planning the next experiment batch requires rescheduling the deferred proposal work.

### D-010: Deliver a TVM-compiled klein pipeline with the planner on top
- **Date**: 2026-10-06
- **Decision**: The thesis delivers two layers.
  - **(a) Engineering artifact:** an MLC-style, TVM-compiled FLUX.2 [klein] pipeline running on CUDA (A100, Jetson), Metal (Apple laptop) and WebGPU (browser).
  - **(b) Research contribution:** the joint reuse/precision/residency planner, built on top of that pipeline.
  - **Baselines:** stable-diffusion.cpp, edge-dit.cpp and PyTorch/diffusers remain baselines.
  - **Target and workload changes:** the Apple laptop target becomes a MacBook Air 15" M5 (24 GB) instead of the M1 MacBook Pro. Wan 2.1 baselines are deferred until the compiled klein pipeline runs.
  - **Schedule:** the revised plan is in [milestones](milestones.md). Weeks may roll over past Dec 11.
- **Why**:
  - The advisor's overview asks for "a universal on-device suite" across NVIDIA, Intel, AMD and Apple hardware and macOS, Linux, Windows, Android and web, citing MLC-LLM ([overview](../../raw/meetings/2026-10-06-advisor-scope.md#project-overview-as-provided-by-prof-haoran-you)). The proposal's planner alone does not produce such an engine ([proposal overview](overview.md#hypothesis)).
  - **Prior-art motivation remains provisional.** The 2026-10-06 README checks considered [MLC-LLM](https://github.com/mlc-ai/mlc-llm), [Web Stable Diffusion](https://github.com/mlc-ai/web-stable-diffusion) and [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp). Those checks alone do not establish that no maintained compiler-based engine covers modern diffusion transformers, or establish research novelty. The decision to build the pipeline is supported by the advisor's confirmation below; a broader prior-art audit remains necessary.
- **Evidence**: the advisor confirmed (a) and (b) ([answer](../../raw/meetings/2026-10-06-advisor-scope.md#scope-question-and-answer)).
- **Scope**:
  - The hypothesis and RQ1–RQ3 are unchanged. WebGPU is added as a target.
  - Roll-over candidates: Android/Vulkan, AMD/Intel, iPhone (Core ML/Core AI), DreamLite, and a compiled Wan pipeline.
  - MLC-LLM's existing Qwen3 support is a candidate text-encoder path, but its match to klein's encoder use is untested.
- **Revisit if**: the Week 3 import gate for klein's transformer in TVM fails, or the advisor names a different priority target.
