# Accelerator optimization review — October 16, 2026

## Shareable summary

The largest gains come from three different mechanisms: eliminating component reloads on the memory-constrained Jetson, reducing actual transformer work with approximate reuse on long schedules, and compiling the remaining computation. A100, Jetson and M5 therefore need different execution plans. The same cache setting is not a portable optimization recipe. M5 timing improvements are promising but several change unrelated stages, so their causal magnitude needs controlled confirmation. Formal quality acceptance remains the main gap between a fast run and a usable optimization.

The immediate compiler opportunity is to make diffusion state lifetimes and memory feasibility explicit, then specialize a small set of measured execution paths. The next prototype should test whether denoising cache state can be released before VAE decoding and whether the recovered headroom permits a faster validated residency plan. Generic fusion, low-bit kernels, caching, and memory planning already exist; their presence alone is not a research contribution.

## Question and scope

Week 2 engine/option coverage and Week 3 compiler preparation; evidence primarily for RQ1, motivation rather than proof for RQ2/RQ3. The proposal hypothesis is: “Jointly planning reuse regions, precision and memory residency can reduce end-to-end latency under a fixed memory budget and a declared quality requirement, compared with fixed configurations or independently selected policies.” [Proposal overview](../wiki/project/overview.md#hypothesis).

The source inventory covers **98 unique completed full runs** from the two chart manifests, with ten measured generations each, plus existing profiling and failure records. This is a numerical inventory and targeted mechanism review, not 98 independent quality evaluations. Current M5 results come from this checkout; newer A100/Jetson evidence comes from the clean `claude/gap-campaign` checkout at the immutable revision above, also present in its remote-tracking branch. Peer evidence is linked to that revision; it has not been merged here. Local run IDs appear in frontmatter; externally versioned runs appear in the appendix. No inference, source merge, commit, push or chart publication was performed for this review.

## What the profiles and stage timings say

### Jetson: prevent reloads before optimizing arithmetic

The newer PyTorch distilled reference spends 63.344 s in `other_ms`, largely sequential component reloads, versus only 1.241 s in text-encoder GPU timing. With exact conditioning reuse, these become 0.031 s and 0.0009 s, while denoising changes only 14.795 → 14.377 s. The 80.315 → 14.911 s improvement therefore principally removes stage-loading work. Adding compilation reduces denoising to 7.250 s and total latency to 7.784 s. Base similarly changes 494.634 → 359.441 → 183.927 s. These are two distinct mechanisms, and the final configuration is a labelled combination, not a compile-only comparison. [Jetson comparison](https://github.com/mfaruqi/on-device-diffusion/blob/d97567a6ad4da5801bafb8e49c76fa6adc501a8c/experiments/compare-jetson-base-caches-reuse-compile.md).

This is stronger causal evidence than attributing the older sd.cpp conditioning result entirely to OS page-cache residency. In the older captured generation, text encoding contains 16.888 s of read-only coverage and step 0 contains 15.101 s, while step 1 has no read coverage and nearly continuous GPU work. That establishes exposed host read intervals, not physical SSD bandwidth or proof that the page cache caused the change. Distinguish component deserialization, CPU conversion, faults, file reads and transfers. [OSRT evidence and method](jetson-flux-klein-003.md).

Resident edge-dit reaches 11.963 s for distilled, but its VAE is tiled and its text representation differs. The separate sd.cpp resident attempts did not finish the full protocol safely. The conclusion is that residency matters, not that one engine universally wins. Disabling flash attention slows steady steps in both sd.cpp and PyTorch by about 30%; tiling is slower locally but can enable a feasible resident pipeline. [Matched-options comparison](https://github.com/mfaruqi/on-device-diffusion/blob/d97567a6ad4da5801bafb8e49c76fa6adc501a8c/experiments/compare-jetson-engines-matched-options.md).

### A100: distinguish faster kernels from fewer computations

The matched torch 2.8 compile run reduces distilled denoising 1.038 → 0.758 s and total 1.290 → 1.022 s; Base total changes 26.477 → 19.525 s. Text and VAE times barely move. Compilation is already a useful baseline and must be included when evaluating a custom compiler. Its warm improvement does not establish cold-start benefit; first-image compilation costs and compiler-cache state must be reported separately. [Compile record](https://github.com/mfaruqi/on-device-diffusion/blob/d97567a6ad4da5801bafb8e49c76fa6adc501a8c/experiments/a100-flux-klein-compile-001.md).

Existing older A100 profiles identify plausible targets: per-step attention is about 37 ms in PyTorch versus 148 ms in sd.cpp, while GEMM totals are similar (124 versus 116 ms). PyTorch has about 83 ms of other GPU work per step; sd.cpp's VAE spends about 404 of 607 ms in im2col. These are reasons to profile attention, layout/cast operations and convolution workspace, not to begin by writing another GEMM. The older trace is not evidence of what remains after the new compile pass. [Profile comparison](compare-a100-pytorch-vs-sdcpp-flux-klein.md).

A100 Base TaylorSeer changes 26.477 → 9.981 s. Its record infers 13 computed and 37 predicted steps from timing, but the current receipt misleadingly counts 100 block entries as full computations. The predicted steps still cost about 78 ms for two CFG calls. Instrument actual prediction branches before claiming exact saved FLOPs. This implementation and M5's attention-output-only TaylorSeer are not interchangeable cache regions. [A100 cache audit](https://github.com/mfaruqi/on-device-diffusion/blob/d97567a6ad4da5801bafb8e49c76fa6adc501a8c/experiments/a100-flux-klein-base-torch28-003.md).

Nunchaku reaches 0.898 s and 15.57 GiB device-wide peak in its A100 distilled run. It demonstrates a functioning low-bit path, but its different quantized checkpoint/software and fixed-seed output variation prevent a matched-quality speedup claim against the BF16 runs. [Nunchaku record](a100-nunchaku-flux-klein-001.md).

### Cache storage can move the bottleneck into a later stage

A100 Base TaylorSeer adds approximately 2.64 GiB of allocated state. Stage-start allocation rises to 17.60 GiB and remains there through VAE decoding/postprocessing; allocated peak becomes 19.97 GiB, versus 17.33 GiB without caching. That is direct lifetime evidence worth investigating. The proposed intervention is to release only cache tensors whose last use is the final denoising step, before VAE execution. It must preserve the supported cache reset semantics, CFG separation and asynchronous completion. Calling `empty_cache()` cannot free tensors that still have live references. [Cache stage/memory record](https://github.com/mfaruqi/on-device-diffusion/blob/d97567a6ad4da5801bafb8e49c76fa6adc501a8c/experiments/a100-flux-klein-base-torch28-003.md#memory-gib).

Hypothesis: freeing that state lowers the VAE peak and may permit a faster memory plan. This is not a promised 2.64 GiB reduction in overall peak: denoising itself peaks around 18.16 GiB, which can become the new maximum. Nor does it necessarily fix Jetson's TaylorSeer failure during initial loading; that requires a separate reference-retention audit. [Jetson failure context](https://github.com/mfaruqi/on-device-diffusion/blob/d97567a6ad4da5801bafb8e49c76fa6adc501a8c/experiments/compare-jetson-base-caches-reuse-compile.md).

### M5: a completed fast run does not isolate its cause

PyTorch distilled is 8.278 s, sd.cpp 16.211 s, and MFLUX BF16 / 8-bit / 4-bit are 80.377 / 71.173 / 10.296 s in the original captured conditions. These are valid observations, not an architectural ranking. Peak allocator bytes, system pressure, quantization scope and implementations differ. [Raw inventory below](#run-inventory).

MFLUX distilled 8-bit tiling changes total 71.173 → 8.607 s, but text changes 17.209 → 0.520 s and denoising 26.831 → 6.836 s even though the option targets VAE decoding. Base 4-bit tiling changes total 151.007 → 111.959 s and denoising 146.880 → 110.409 s. Tiling reduces reported MLX allocator peak by about 0.826 GiB for either precision. Hypothesis: lower peak/persistent allocator pressure can improve later generations, but background or thermal history can produce similar signatures. The present captures do not separate those explanations. [Distilled tiling](m5-mflux-flux-klein-006.md), [Base tiling](m5-mflux-flux-klein-base-005.md).

Swap occupancy is not swap traffic. A large swap file can remain after pressure subsides. To explain latency, correlate stage intervals with swap-in/out deltas, faults, compression, memory pressure and device execution. Never equate MLX/PyTorch allocation with whole-system memory, or add allocated and reserved values.

M5 PyTorch Base TaylorSeer achieves 92.474 s versus the 167.101 s reference; distilled TaylorSeer instead takes 57.556 s versus 8.278 s under much greater pressure. This is not evidence that TaylorSeer intrinsically costs seven times as much on a four-step model. Distilled compile failed the predeclared numerical gate; Base compile passed narrowly. Both facts belong in a feasibility table, not a chart of accepted speedups. [TaylorSeer](m5-flux-klein-005.md), [compile gate](m5-flux-klein-004.md), [Base compile](m5-flux-klein-base-004.md).

## Quality is a constraint, not a footnote

| Evidence | What it establishes | What it does not establish |
|---|---|---|
| Same-engine exact conditioning image match | Sampled repeat semantics preserved; first miss still costs normal encoding | Performance on arbitrary new prompts, cache eviction or a broader prompt set |
| Compile numerical smoke / deterministic images | A configured local tolerance or repeatability check | Universal numerical equivalence or perceptual quality acceptance |
| EasyCache / TaylorSeer / MagCache images | Functional outputs and visible failure modes | A matched-quality Pareto frontier |
| Low-bit checkpoint output | Feasible compressed execution | Equivalent quality or quantization-only attribution across engines |
| Tile-local-normalization output | Memory-saving approximate decode works | Exact equivalence to full-image normalization |

Jetson edge-dit Base MagCache is much faster (73.108 s versus 232.499 s), but the sign text is deformed; the fastest row is not automatically eligible. A100 four-step TaylorSeer visibly changes lettering and scene tone. MFLUX 4-bit samples have text errors; some no-cache references also miss the requested text. Use multiple development/calibration prompts and seeds, alignment/composition/OCR checks, paired diagnostics, and structured blinded review; declare acceptance before choosing a winner. Do not open the held-out quality set before the scheduled evaluation. [Jetson cache comparison](https://github.com/mfaruqi/on-device-diffusion/blob/d97567a6ad4da5801bafb8e49c76fa6adc501a8c/experiments/compare-jetson-base-caches-reuse-compile.md), [A100 four-step cache](https://github.com/mfaruqi/on-device-diffusion/blob/d97567a6ad4da5801bafb8e49c76fa6adc501a8c/experiments/a100-flux-klein-torch28-004.md), [MFLUX quality](m5-mflux-flux-klein-base-003.md).

## What is already known, and the narrower research opportunity

| Idea | Prior art / current evidence | Consequence |
|---|---|---|
| Joint caching and quantization | [CacheQuant](https://arxiv.org/abs/2503.01323) jointly optimizes the cache schedule and quantization error; [Q&C](https://arxiv.org/abs/2503.02508) treats calibration and accumulated error interactions | Combining two knobs is not a novelty claim. |
| Diffusion tensor lifetimes and memory planning | [Xema](https://arxiv.org/abs/2607.11136) describes trace-guided pressure mitigation, static layout and plan selection | Generic lifetime-aware planning is already studied. A full paper/code comparison is required. |
| Low-bit arithmetic with efficient execution | [SVDQuant / Nunchaku](https://arxiv.org/abs/2411.05007) co-designs quantization and fused low-rank/low-bit execution | Stored bit-width alone does not predict speed; include packing, conversion and memory traffic. |
| Shift-add and layer sensitivity | [ShiftAddLLM](https://arxiv.org/abs/2406.05981) reparameterizes LLM weights into binary components and scales, with sensitivity-based allocation | Diffusion transfer is a hypothesis. Benchmark real DiT matrix shapes against optimized tensor-core/Metal paths before a port. |

These references were screened at abstract level for overlap, not exhaustively reviewed for priority. Candidate contribution: a diffusion-aware compiler selects which intermediate regions to retain, at which representation/precision, and for how long, jointly with weight/workspace residency under a physical memory budget and calibrated error limit. It specializes refresh/reuse paths and enforces their lifetimes across CFG branches and stage transitions. The differentiator must be demonstrated over tuned fixed policies, independent selection and the closest existing joint methods. Cross-backend portability is useful engineering but not sufficient novelty by itself.

A useful cost model must include saved compute **minus** probe/prediction/conversion/reload costs and any induced pressure penalty. Its memory constraint is the maximum over time of simultaneously live weights, activations, workspaces, caches and transition buffers, plus reserve. Reuse hit rate, first-request cost and compilation amortization belong in the workload definition. It should be allowed to select no cache.
